# SugarShield dataset

A real, labeled dataset + reproducible pipeline for fine-tuning a small
sugar-risk-detection model, and a frozen benchmark to evaluate it (and the
existing deterministic rule engine) against.

## Source data: why GroceryDB, not the Open Food Facts REST API

The original plan for this dataset was to pull product data live from the
Open Food Facts REST API (`world.openfoodfacts.org`). That domain (and every
`*.openfoodfacts.org`, `openfoodfacts.github.io`, `huggingface.co`,
`wikipedia.org`, and `kaggle.com` host) is blocked outright by this build
environment's network egress policy — every request, including a bare HEAD,
comes back as a policy-level 403 from the egress proxy. This was verified
with `curl`, Python `requests`, and the agent's own `WebFetch` tool before
switching sources. It is not something the fetch script can work around.

`git clone` against public GitHub repositories, and plain HTTPS GETs to
`raw.githubusercontent.com`, **are** reachable from this environment, so the
dataset instead uses **[GroceryDB](https://github.com/Barabasi-Lab/GroceryDB)**
(Barabási Lab, Northeastern University; MIT license), a real dataset of
**50,638 products scraped from Target, Walmart, and Whole Foods**, published
alongside the lab's Nature Food / Nature Communications papers on food
processing and nutrition. `data/scripts/fetch_openfoodfacts.py` performs a
real `git clone --depth 1` of that repository (no synthetic fallback) and
joins its two source files:

- `data/GroceryDB_foods.csv` (50,638 rows: name, store, brand, harmonized
  category, and nutrition-per-100g including total sugars, protein, etc.)
- `data/UpdatedProductIngredients_11_15.zip` → `UpdatedProductIngredients_11_15.json`
  (~325MB uncompressed): the real per-product ingredient list, as a nested
  `ingredient_tree` (top-level ingredients with recursive `sub_ingredients`,
  in label order) for a subset of ~42.5k of those products.

The join key is `original_ID`. `ingredients_raw` is reconstructed by walking
each `ingredient_tree` in `order`, rendering the verbatim label text
(`original_text`) for each node, and nesting any `sub_ingredients`
recursively in parentheses — e.g. `"Whey Crisp (Whey Protein Concentrate,
Rice Flour), Almonds"` — which mirrors how a real nutrition-facts panel lists
sub-ingredients. **Every `"source": "grocerydb"` record in this dataset is a
real product**, not synthetic.

GroceryDB's nutrition columns are per-100g, not per-serving, so every
GroceryDB-derived record's `nutrition.serving_size` is honestly recorded as
`"100g"` and `added_sugars_g` is left `null` (GroceryDB does not separate
added sugar from total sugar).

## Repository structure

```
data/
  raw/                        # capped, per-category joined GroceryDB pulls + manifest.json
  processed/
    cleaned_candidates.jsonl  # intermediate: cleaned/deduped, category not yet finalized
    all_records.jsonl         # final labeled bulk dataset (source of train/validation pool)
    dataset_stats.json        # generated by dataset_stats.py
  train/train.jsonl
  validation/validation.jsonl
  gold/gold.jsonl             # frozen benchmark, verified:true, zero overlap with train/val
  scripts/
    fetch_openfoodfacts.py    # clones GroceryDB, joins, category-buckets -> data/raw/
    grocerydb_common.py       # GroceryDB category mapping + ingredient-tree flattening
    lexicon.py                # Python port of lib/lexicon.ts
    risk_engine.py            # Python port of lib/riskEngine.ts (STRICT mode)
    clean_and_normalize.py    # dedup + text cleaning -> cleaned_candidates.jsonl
    label_records.py          # runs risk_engine over every candidate -> all_records.jsonl
    build_gold_set.py         # assembles the frozen gold/gold.jsonl benchmark
    split_dataset.py          # gold-exclusion + stratified 90/10 train/validation split
    detect_leakage.py         # hard PASS/FAIL check: zero gold vs train/val overlap
    dataset_stats.json        # (see processed/dataset_stats.json for the actual output)
```

## Record schema

Every record in `processed/all_records.jsonl`, `train/train.jsonl`,
`validation/validation.jsonl`, and `gold/gold.jsonl` matches:

```json
{
  "id": "gdb_<original_id> | gold_v1_<eNNN> | manual_<NNN>",
  "product_name": "string",
  "brand": "string or null",
  "category": "soda | juice | cereal | protein_bar | yogurt | sauce | snack | dessert | bread | breakfast | protein_product | kids_food | healthy_marketed | sugar_free | artificially_sweetened | natural_sugar | other",
  "ingredients_raw": "string",
  "normalized_ingredients": ["lowercased", "split", "ingredient", "tokens"],
  "nutrition": { "serving_size": "string or null", "total_sugars_g": "number or null", "added_sugars_g": "number or null" },
  "contains_added_sugar": true,
  "contains_hidden_sugar": false,
  "contains_artificial_sweetener": false,
  "contains_natural_sugar": false,
  "detected_sugars": ["..."],
  "artificial_sweeteners": ["..."],
  "risk_level": "SAFE | LOW | MODERATE | HIGH | VERY_HIGH",
  "explanation": "one short sentence",
  "source": "grocerydb | manual_gold | sugarshield_v1_eval",
  "verified": true
}
```

Note the `source` enum differs from the dataset's original spec (which
assumed Open Food Facts): `"openfoodfacts"` is replaced by `"grocerydb"`
throughout, for the reason explained above. `"sugarshield_v1_eval"` and
`"manual_gold"` are unchanged and only ever appear in `gold/gold.jsonl`.

## How bulk labels were generated — silver labeling, not human verification

Every `"source": "grocerydb"` record in `processed/all_records.jsonl` (and
therefore `train/` and `validation/`) has `"verified": false`. Its
`risk_level`, `detected_sugars`, `artificial_sweeteners`, `contains_*` flags,
and `explanation` are **not** independently human-checked — they are
computed by running the *same deterministic rule engine the live product
uses* over each record's real ingredient text. This is intentional
distillation / silver-labeling, done so a fine-tuned model trained on this
data learns to approximate the shipped rule engine's behavior on a much
larger, more realistic ingredient-text distribution than the rule engine's
own 15-case eval set covers. It is explicitly **not** a claim that a human
checked each bulk label.

Concretely, `data/scripts/lexicon.py` and `data/scripts/risk_engine.py` are
faithful line-by-line Python ports of `lib/lexicon.ts` and
`lib/riskEngine.ts`:

- `lexicon.py` reproduces every `added_sugar`, `hidden_sugar`,
  `artificial_sweetener` (including the plant-sweetener terms: stevia, monk
  fruit, allulose), `sugar_alcohol`, and `natural_sugar_context` term and
  reason string from `lib/lexicon.ts`, sorted longest-term-first for the same
  "most specific match wins" behavior.
- `risk_engine.py` reproduces `lib/normalizeText.ts`'s normalization,
  `lib/normalizeIngredients.ts`'s comma/semicolon/parenthesis splitting,
  `detectMatches`'s per-token word-boundary matching, `scoreRisk`'s point
  weights (added-sugar-count tiers, the hidden-sugar bonus, the top-20%
  prominence bonus, and the **STRICT**-mode artificial-sweetener/sugar-alcohol
  weights — STRICT is the current live default), `riskLevelFromScore`'s
  SAFE/LOW/MODERATE/HIGH/VERY_HIGH score bands, and `buildExplanation`'s
  one-sentence summary logic.

This port was spot-checked against the live TypeScript engine's actual
behavior on several ingredient strings (including all 15 legacy eval cases)
before being used to label the bulk dataset.

### Category assignment for GroceryDB records

GroceryDB's own "harmonized single category" (53 categories, e.g.
`drink-soft-energy-mixes`, `snacks-bars`, `dairy-yogurt-drink`) is mapped
onto the SugarShield category enum by `grocerydb_common.py`. A handful of
enum values are cross-cutting properties that can only be decided *after*
running the risk engine (a product only belongs in `sugar_free` if its name
says so; `artificially_sweetened` only if it has a sweetener but no real
sugar; `healthy_marketed` only if it's marketed with health language *and*
still has 2+ real added-sugar sources) — that reassignment happens in
`label_records.py`, after labeling, via
`grocerydb_common.refine_category_post_label`. Categories with no direct
GroceryDB analogue (meat, seafood, cheese, spices, coffee, tea, canned
goods, prepared meals, etc.) fall into `"other"`, capped low so it can't
dominate the dataset.

## Gold benchmark (`data/gold/gold.jsonl`) — 59 records, frozen, `verified: true`

Built by `build_gold_set.py` from three sources:

1. **15 records ported from `data/evalSet.json`** (`source:
   "sugarshield_v1_eval"`, id `gold_v1_e00N`). These are the pre-existing
   15-case eval set's ingredient text, **re-scored fresh through the ported
   rule engine** — their old PASS/WARN/FAIL verdicts are not reused.
2. **39 curated real GroceryDB records** (`source: "grocerydb"`,
   `verified: true` after manual eyeballing), chosen to cover the specific
   hard cases called out for this benchmark: a diet soda with only an
   artificial sweetener and no real sugar (`Diet Coke`), a diet soda with
   stacked artificial sweeteners, an artificially-sweetened juice, a real
   high-fructose-corn-syrup product, a real fruit-juice-concentrate product,
   an isolated stevia-only case, an isolated monk-fruit-only case, a product
   with 4 stacked sugar aliases in one ingredient list (sugar, maltodextrin,
   dextrose, honey), three "misleading healthy" products (a "Healthy
   Grains" bar, a "GoLean" cereal, and a "Lower Sugar" oatmeal — all three
   still contain 2+ real added-sugar sources despite the health framing),
   plus 2 additional clean examples per category enum value for general
   coverage.
3. **5 hand-composed records** (`source: "manual_gold"`) for concepts real
   data in this pull didn't isolate cleanly: standalone dextrose, standalone
   fructose, standalone maltodextrin (a hidden-sugar-only case), standalone
   corn syrup solids (a hidden-sugar-only case), and standalone erythritol.
   These are explicitly synthetic and labeled as such — never claimed as
   real products.

Every gold record's `risk_level`/`detected_sugars`/etc. is computed by the
*same* `risk_engine.py` used for the bulk data, so gold labels are the
engine's actual calibrated output, not hand-guessed — including for cases
(diet soda, stevia, monk fruit, erythritol, coconut water) where the current
rule engine's STRICT-mode weights are deliberately lower for
artificial-sweetener/sugar-alcohol signals than a naive "any sweetener =
FAIL" classifier would give.

**Gold ids and (product_name, ingredients_raw) pairs never appear in
train/validation** — enforced by `split_dataset.py` (exclusion) and checked
by `detect_leakage.py` (verification). See exact counts below.

`manual_gold` — 54/59 (91.5%) are real products, 5/59 are hand-composed.

Train/validation are 100% `source: "grocerydb"` (real products), 0%

Note: `lib/lexicon.ts` (and its Python port `lexicon.py`) were adjusted
after the first labeling pass to drop `"caramel"`/`"caramel color"` — that
term was flagging zero-sugar diet sodas as "contains added sugar" purely
because of E150 coloring, which is exactly the over-warning failure mode
this dataset exists to fix. `label_records.py` through `dataset_stats.py`
were re-run after the fix; the counts below are from that final run.

## Re-running the pipeline

```bash
cd data/scripts
python3 fetch_openfoodfacts.py     # clones GroceryDB, joins, category-buckets -> ../raw/
python3 clean_and_normalize.py     # clean + dedupe -> ../processed/cleaned_candidates.jsonl
python3 label_records.py           # ported rule engine -> ../processed/all_records.jsonl
python3 build_gold_set.py          # -> ../gold/gold.jsonl
python3 split_dataset.py           # -> ../train/train.jsonl, ../validation/validation.jsonl
python3 detect_leakage.py          # hard PASS/FAIL check
python3 dataset_stats.py           # -> ../processed/dataset_stats.json
```

`fetch_openfoodfacts.py` caches its GroceryDB clone and unzipped ingredient
JSON under a scratch directory (`$SUGARSHIELD_SCRATCH`, default a
session-local scratchpad) rather than inside this repo, so re-running it
doesn't re-clone or re-unzip 325MB every time.
